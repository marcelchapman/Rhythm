# Rhythm 0.1 implementation decisions

## Desktop stack

Electron 44, React 19, TypeScript, and Vite implement the approved desktop prototype. Electron's bundled Chromium gives macOS and Linux the same layout and audio API instead of relying on different system WebView codec support. The cost is a larger download and memory footprint. This is a desktop decision: Electron does not target Android or iOS.

Tauri was considered for its smaller runtime and mobile targets. For this milestone, its system-WebView differences and platform-dependent audio support add risk to the central playback requirement. Qt would require another UI implementation approach to match the supplied composition. Native Swift alone would not serve Linux. These trade-offs favor a working, consistent desktop core now.

The renderer and shared DTOs contain no filesystem or SQLite access. `src/domain/library.ts` owns indexing, normalization, persistence, and playlists independently of Electron. A future mobile client can share TypeScript models and domain rules, but needs filesystem, database, and playback adapters; this is a credible reuse boundary, not a claim that the desktop implementation runs unchanged on mobile.

## Data and music safety

The user chooses a directory for `rhythm.sqlite`. Source music directories are chosen separately. A small pointer in Electron's application-data directory remembers the library. No library or source directory is supplied by the distribution. Tests override only application data using `RHYTHM_DATA_DIR` and use temporary libraries.

SQLite uses WAL, foreign keys, an application ID, and schema version 3. Unrelated databases and newer schema versions are rejected. The version-1 migration adds nullable BPM/bit rate, comments, codec, and an extraction-version marker in one transaction. No existing rows are replaced. A rescan reparses older extraction versions even when source size/mtime is unchanged, preserving favourites, added dates, IDs, and playlist links. Absent numeric tags remain null and absent strings remain empty. The main process owns the database. Scanning asynchronously walks directories and reads metadata using `music-metadata`; database statements are synchronous, so very large libraries can still cause UI latency during snapshot generation. Scans are serialized. Read failures are bounded to 100 reported issues per scan.

External source files are never written, renamed, moved or deleted. Rhythm's filesystem management authority ends at the configured Rhythm Media environment. Locate File and consolidation grant read/copy access to external files, never ownership or permission to mutate them. Ordinary managed additions require the explicit copy-on-add setting; managed recovery and consolidation are separately invoked copy operations. Only verified copies become managed locations. Symlinks and hidden entries are skipped. Canonical paths prevent duplicate indexing of the same path. File size and modification time avoid repeated metadata parsing. Existing path-hash IDs are preserved; new tracks use random path-independent 256-bit IDs. Paths are device-local locations, not portable identity. Unreconciled external moves still create a new record; missing records and playlist references are retained, not silently discarded. Matching files by content after moves is deferred.

External audio/folder/playlist drops use Electron's `webUtils.getPathForFile` inside the sandboxed preload. Only bounded absolute disk paths reach the main process. M3U/M3U8 files route to the playlist importer; other paths reach the explicit-add scanner, which applies the opted-in copy policy. Unsupported files are skipped. Referenced inputs remain rescan sources; managed imports record their media root instead of watching external source folders for new copies. Internal drags carry validated track IDs, not arbitrary file-operation instructions. Playlist append checks current database contents in a transaction, preserves order, and deduplicates additions; it never overwrites a playlist from a stale renderer snapshot.

Albums group by album artist, title, and album directory. Compilation tags resolve Album Artist to Various Artists. `CD1`/`Disc 1` folders normalize to their parent. Different directory editions with identical metadata remain distinct. Artwork is cached in SQLite only for supported raster formats up to 10 MB per track. External cover files are not currently searched.

## Managed Rhythm Media foundation

Schema 3 adds transactional ownership records (`track_locations`), logical UUID media roots (`media_roots`), separate device-local root mappings (`media_root_locations`), and an import journal (`managed_imports`). Legacy tracks migrate as referenced. A managed location records root ID plus relative path; the existing `tracks.path` remains the resolved device-local playback/indexing path. Root mappings, filesystem device/inode values, source receipts and absolute paths are local state and must not be blindly synchronized. These tables are not a synchronization protocol.

Per-library media settings live in SQLite, independently of profile-global Track List preferences. A native folder chooser supplies the root; the renderer can only toggle the two typed booleans. Add Music and audio/folder drops call `Library.add`. Rescan and M3U import call reference-only `Library.scan`. Existing known managed tracks stay managed on all scan paths. Matching source receipts reuse a managed track for playlist imports instead of duplicating its original. Explicitly adding an existing referenced file with copying enabled changes its database location to the verified copy while retaining ID, favourites, added date, playlists and queue. No original file is moved or reorganized.

`media-plan.ts` is a pure planner. `managed-copy.ts` owns root containment/identity checks, streaming SHA-256, exclusive private staging, source/copy verification, directory/file synchronization and no-overwrite publication. Publication hard-links a fully copied private staging inode into its final destination; it never hard-links the original. Managed files therefore have independent bytes/inodes from their external sources. SQLite commits track metadata, ownership, rescan root and completed receipt together. A failed database commit leaves a journaled copy for explicit retry, never a false managed record. Pending published files are excluded from ordinary scanning, including case-insensitive path aliases.

Retries verify receipt identities/hashes and reuse their publication; collisions use numbered suffixes and never overwrite an unrelated destination. Missing staging links can recover a verified publication or recopy the original on explicit retry. Only receipt-owned private `.partial` links are removed during retry/cleanup. No existing audio destination is deleted on rollback. No automatic recovery scan, generic orphan deletion, adoption by folder membership, or existing-file reorganization runs. Unknown files already inside the media root remain referenced. Changing the root or organization toggle affects future additions only.

Locate File uses a native audio-file picker and preserves the existing track ID. Referenced recovery validates/parses the chosen file and updates the device-local reference without copying, regardless of copy-on-add. Managed recovery uses the current media root and existing planner/staging/hash/journal pipeline to copy a selected recovery source, regardless of copy-on-add. Selecting a valid file restored at its expected current-root managed path revalidates it in place. A file already linked to another track or a receipt belonging to another identity is rejected rather than merging/deleting identities. No automatic filesystem search or matching by guessed metadata is implemented.

`Library.consolidate` shares the serialized indexing/copy pipeline with imports and recovery. Track selection, album context and whole-library commands supply existing identities; only referenced rows are processed. Each verified publication and ownership transition commits separately. Successful tracks survive another track's failure. Subsequent runs skip managed rows and retry the remaining referenced rows; unfinished publications are reused through receipt identity/hash checks. Referenced files already inside Media are independently copied, not silently adopted. Rescan remains non-copying. No schema beyond version 3 is required for these workflows.

Playback/access errors check the known local file and expose Locate File for missing tracks. The original acceptance defect was a retained Chromium media error: restoring/rescanning cleared SQLite missing state but did not reload the stable-ID URL. The renderer now reloads on recovery/location/missing-state changes and explicitly reloads an errored same-track Play request. A decoder failure alone is not proof of a missing file. Queue/current ID and saved state remain intact; path changes preserve the current playback position. Native track menus expose Locate for one missing track and consolidation only when the selection contains referenced tracks. Album cards support the same native machinery. File/Library Settings → Consolidate Library requires a copy-only confirmation, then shows aggregate results and bounded failure details.

The native Track Info command carries one context-track ID separately from the bulk selection. TrackList passes the clicked row (keyboard activation uses the existing selected-row target); the main process verifies membership. Bulk actions retain the entire selection. Track Info refreshes the existing snapshot/availability and renders only stored metadata in a read-only Modal. No tag-writing bridge or schema expansion is introduced. A canonical-path collision during Locate remains an explicit error that preserves both records. Direct referenced recovery is verified by exact one-row identity/state/source-integrity and real playback checks with copy-on-add OFF/ON; the user's latest retest confirms both entry points work. The initially reported duplication was not reproducible as a direct Locate defect; an independently demonstrated rescan-before-Locate collision is not claimed as its cause.

The full naming, failure, source-integrity and manual acceptance contracts are in [ITERATION-3.md](ITERATION-3.md). Before tag writing/deletion, add operation-specific confirmation/recovery, current file-identity checks and robust handling of hostile concurrent filesystem changes; the foundation does not grant a destructive capability.

## Playback and state

HTMLAudioElement performs local decoding. `rhythm-media://track/<id>` resolves only indexed IDs, never renderer-supplied filesystem paths. Explicit byte-range responses support seeking without loading entire files into memory. Missing files return 404; decoding failures show an actionable error. AIFF metadata can be indexed but Chromium may not play AIFF. DRM content is unsupported.

The persistent player records queue, current track, position, volume, shuffle, repeat mode, and navigation. State is debounced and checkpointed every four seconds; a forced termination can lose the last few seconds. Reopening restores selection and position but does not start playback automatically. Queue edits and shuffle/repeat are local to the listening session and persist with that session. Playlist edits use a SQLite transaction.

## Desktop boundary

The renderer is sandboxed, uses context isolation, and has no Node integration. A narrow preload bridge exposes library actions. IPC checks the requesting frame URL. Custom protocols serve bundled files and indexed media; networking, popups, navigation away from the app, and runtime permission requests are denied. All fonts and UI assets are local. Music metadata renders as React text, not HTML. No telemetry, cloud requests, or source-artifact reuse is implemented.

Track context menus are native Electron menus built in the main process from indexed IDs. A typed action event dispatches existing renderer transport and playlist commands; only read/relink and verified-copy filesystem actions are present; no source-mutation commands are exposed. File → New Playlist uses the same creation form as the sidebar. The shared modal installs its focus trap once per mount and reads the current close callback through a ref, avoiding focus resets while typing or selecting a playlist.

The Songs table renders only its visible rows plus overscan, with stable row height, a sticky first column/header, and horizontal metadata scrolling. Sorting/filtering is memoized separately from playback progress. Album/queue detail lists initially render 200 entries and extend on demand. This bounds DOM work but does not make snapshot transfer or in-memory sorting independent of total library size.

The reusable `TrackList` component replaces SongsTable and is used by Songs, playlist contents, Artist/Genre track drill-downs, Favourites, search, and library list mode. Artist/Genre grouping and album navigation remain. One application/profile-global `view-preferences.json` stores version-2 `trackList.columns.{order,widths,hidden}` independently of SQLite/player state. The first remembered/selected library's legacy Songs order migrates once if no global preference file exists. A shared normalizer appends new column IDs, removes unknown/duplicate IDs, clamps widths, and keeps Title visible. Serialized atomic preference updates merge partial changes; normal quit flushes them. Hiding a column preserves its position/width. Header reorder buttons, sibling pointer-captured resize handles, and row drags have distinct hit areas/transfer types. Oversized first columns stop sticking so horizontal access remains possible.

Presentation does not carry content state: local sort/selection/scroll belong to the current Track List, not the global layout. Playlists default to stored membership order and can restore it after local header sorting; Songs/album sort settings never reorder playlist storage. Year uses already indexed metadata. Compact side-panel album/queue rows remain their existing contextual presentation.

`src/domain/m3u.ts` parses/serializes UTF-8 playlist data independently of Electron. `src/domain/playlist-files.ts` resolves local references, calls the existing scanner, creates the playlist and its ordered unique membership transactionally, and writes exports atomically. Local file URLs are accepted; remote protocols are never fetched. Import names are collision-safe. Export uses relative references only for audio within the destination directory tree; other audio uses absolute paths. Symlink destinations and known source-audio hard links are rejected, and the main-process save dialog only produces `.m3u8`. File-menu integration uses narrow IPC methods with native dialogs and operation guards against overlapping imports/library switches. An early `open-file` listener and platform-neutral inbox retain OS/startup requests until initialization, renderer readiness, and library selection. Canonical-path pending/in-flight/two-second recent deduplication coalesces lifecycle deliveries. Closing windows suspend consumption; queued macOS file opens recreate the window. File associations declare only M3U/M3U8 Viewer/Alternate, without default-handler registration. The renderer receives reports and never gains arbitrary filesystem write access.

## Packaging

`electron-builder` produces macOS app bundles, DMG and ZIP distributions, and Linux AppImage/DEB packages. The lockfile pins dependency resolution. An override updates the packager's proxy dependency to remove a vulnerable transitive dependency. Revisit it when upstream no longer needs the override.

Local macOS artifacts are unsigned and unnotarized because no signing identity or credentials were supplied. Linux packages can be cross-built here, but must be runtime-tested on Linux; `.github/workflows/build.yml` provides target-OS checks and packaging without publishing releases. No workflow has been run remotely as part of this implementation.
